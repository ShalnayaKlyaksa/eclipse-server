# Аудит промышленного кода

Дата: 25 октября 2026 года. Проверялась текущая рабочая копия, включая существующие
незакоммиченные изменения. Исходный код в ходе аудита не менялся.

## Вывод

Промышленность выглядит как прототип, в котором уже накопились несогласованные
правила работы с ресурсами и состояниями. Основа пригодна для развития: есть
разделение Shared/Server/Client, YAML-рецепты, контейнеры, события и отдельная сеть.
Главная проблема расширения — разные участки по-разному понимают один материал,
наличие места, доступность рецепта и момент запуска операции.

В трёх каталогах Industrial сейчас 67 файлов C#, 5838 строк. Само количество файлов
не является недостатком ECS. Две системы процессора вместе содержат 1178 строк;
в них смешаны взаимодействия, подбор рецепта, движение предметов, конфигурация портов,
обновление вида и подготовка интерфейса.

Ниже — выводы по коду, а не результаты профилирования большого завода. Доказана
наличествующая лишняя работа; её вклад в миллисекунды тика и сетевой трафик не измерялся.

## Замечания

### 1. [P1] Обычная добытая руда не соответствует промышленным рецептам

Место: `Content.Shared/_Eclipse/Industrial/SharedIndustrialProcessorSystem.cs:337–363,
414–438`; `Resources/Prototypes/_Eclipse/Industrial/recipes.yml:13`;
`Resources/Prototypes/ore.yml:7`.

Добыча выдаёт `SteelOre1`, а рецепт дробилки требует `SteelOre`. Сравнение выполняется
по точному ID прототипа сущности, без учёта `StackTypeId`. Одинаковый тип стека не
помогает: `CanAcceptInputProto(machine, "SteelOre1")` для дробилки возвращает false.
Разделение стека тоже создаёт сущность из `StackPrototype.Spawn`, то есть вариант `1`.

Похожий разрыв есть дальше: плавильня выдаёт `SheetSteel1`, а верстак считает
ингредиент `SheetSteel` по точному ID. Слияние с подходящим исходным стеком может
замаскировать проблему, но самостоятельная цепочка производства ненадёжна.

Исправление: различать требования к типу материала/стека и к конкретному предмету.
Для стека опираться на StackTypeId; для штучных компонентов сохранять явную проверку
предмета. Простая замена всех ID на суффикс `1` оставит проблему других вариантов.

### 2. [P1] Холодная загруженная центрифуга не запускается после прогрева

Место: `Content.Server/_Eclipse/Industrial/IndustrialProcessorSystem.cs:152–161,
186–195`; `Content.Server/_Eclipse/Industrial/IndustrialHeatBufferSystem.cs:118–120`.

Если загрузить подходящее сырьё при температуре ниже порога, TryStartProcessing
завершится без запуска. После нагрева температура просто меняется. Система процессора
для IsWorking=false обновляет только внешний вид и не пытается начать работу.
Подписки на достижение рабочей температуры нет. Нужна дополнительная операция с
контейнером, чтобы повторно вызвать запуск.

Исправление: явное событие перехода в рабочий тепловой режим и повторная проверка
готовности станка. Температуру менять через TemperatureSystem; прямое присваивание
также обходит штатные события изменения температуры.

### 3. [P2] Неудачная передача превращается в полный поиск каждый кадр

Место: `Content.Server/_Eclipse/Industrial/ItemPipeNetworkSystem.cs:242–247,
256–301`.

Таймер сбрасывается только при успешном TryTransferOne. После истечения задержки
пустая или заблокированная сеть с неиспользованным лимитом повторяет попытку каждый
Update. Попытка заново обходит трубы, ищет соседние станки, создаёт List/HashSet,
сортирует источники и, при наличии продукции, аналогично ищет получателей. Далее
перебираются пары источников и приёмников. Неизменившаяся топология вычисляется снова.

Исправление: ограничить частоту самих попыток независимо от успеха; хранить список
подключённых станков до изменения топологии/портов. Проверять наличие продукции
и свободную ёмкость непосредственно перед переносом.

### 4. [P2] Одно изменение вызывает несколько пересборок той же сети

Место: `Content.Server/_Eclipse/Industrial/ItemPipeNetworkSystem.cs:65–93`;
`Content.Server/_Eclipse/Industrial/ItemPipeSystem.cs:39–64`;
аналогичный код в `LiquidPipeNetworkSystem.cs:61–106`.

RebuildAdjacentPipeNetworks объединяет connected-соседей и всех соседей через Concat;
одни и те же трубы попадают в обход дважды. Каждая запускает полный flood fill.
RebuildNetworksNearProcessor помечает обработанной только стартовую трубу, поэтому
разные соседние трубы одной сети снова перестраивают весь компонент связности.
Дополнительно изменение трубы вызывает обновления соседних станков, а те запускают
свои пересборки. Переключение порта станка тоже перестраивает граф труб, хотя
ArePipesConnected не зависит от портов станка.

Исправление: одна отложенная пересборка на затронутый компонент связности, с учётом
разделения сети при удалении. Порты меняют список конечных устройств; для них не
требуется заново вычислять связность самих труб. Сначала достаточно убрать повторные
старты, затем вводить пакетную обработку изменений.

### 5. [P2] Верстак не суммирует неполные стеки

Место: `Content.Server/_Eclipse/Industrial/IndustrialWorkbenchSystem.cs:180–187`;
`Content.Client/_Eclipse/Industrial/UI/WorkbenchCraftMenuPresenter.cs:279–286`.

При потребности в 15 единицах стеки 10 и 5 игнорируются по отдельности: условие
stack.Count < needed возвращает управление до уменьшения remaining. Материала
достаточно, но изготовление недоступно. В карточке CountAvailable суммирует количество
и может показывать 15/15 одновременно с недоступностью рецепта.

Исправление: единый подсчёт доступного количества и план расходования для клиента
и сервера, с окончательной серверной проверкой. У процессоров TryMatchRecipe также
ищет всю нужную порцию в одной сущности: это ограничение нужно устранить перед
добавлением многокомпонентных и пакетных рецептов.

### 6. [P2] Проверка возможности слияния позволяет превысить число слотов

Место: `Content.Shared/_Eclipse/Industrial/SharedIndustrialProcessorSystem.cs:86–92,
127–137`; `Content.Server/_Eclipse/Industrial/IndustrialProcessorSystem.cs:110–113`.

При заполненном контейнере разрешается вставка, если CanMergeIntoContainer нашёл
совместимый стек со свободным местом. Затем TryDropIntoContainer переносит новую
сущность целиком; слияние здесь не выполняется. Штатный метод рук также не сливает
стеки. В контейнере может оказаться больше сущностей, чем MaxInputSlots. BuildSlotStates
отображает только первые maxSlots, поэтому лишние предметы не видны в окне.

Исправление: действительно сливать стеки через SharedStackSystem.TryMergeStacks до
вставки оставшегося количества, либо запретить вставку новой сущности при заполнении.
Ручной и трубный пути должны соблюдать одно правило ёмкости.

### 7. [P2] Теплообменник создаёт нагрев независимо от энергии источника

Место: `Content.Server/_Eclipse/Industrial/IndustrialHeatBufferSystem.cs:66–94,
115–120`.

PlasmaFlowing определяется суммой плазмы во входном и выходном узлах, без проверки
реального потока. Даже при пустом inlet и небольшом запасе плазмы в outlet выполняется
TransferHeatToLinkedProcessors. Температура станков растёт к OperatingTemperature
независимо от фактической температуры буфера; энергия из газа/буфера не вычитается.
Отдельно MathF.Max(OperatingTemperature, gasTemp) позволяет нагревать сам буфер от
холодного газа до заданной высокой температуры.

Исправление: определить источник тепловой энергии. Для теплообменника переносить
конечное количество энергии от более горячего тела к холодному. Если это нагреватель,
явно потреблять топливо или электричество. Не использовать наличие плазмы как
замену одновременно расходу топлива и передаче тепла.

### 8. [P2] Прогресс вызывает полный снимок интерфейса каждый тик

Место: `Content.Server/_Eclipse/Industrial/IndustrialProcessorSystem.cs:164–169,
547–564,597–623`; `Content.Shared/_Eclipse/Industrial/IndustrialProcessorUi.cs`.

Для работающего станка компонент помечается Dirty каждый кадр. Если интерфейс открыт,
каждый кадр дополнительно создаются BUI-state, два массива слотов и объекты для всех
слотов, заново вычисляются имена. Класс состояния не переопределяет Equals, поэтому
штатный SetUiState не распознаёт новый экземпляр как эквивалент старого. На клиент
отправляется полное состояние ради изменения прогресса.

Проверка IsUiOpen уже присутствует: закрытым окнам эти массивы не строятся. Эту
существующую оптимизацию нужно сохранить.

Исправление: список слотов обновлять при изменении содержимого; прогресс отображать
по времени начала/завершения с интерполяцией или обновлять с ограниченной частотой.
Отдельно исключить поиск рецепта из покадрового обновления вида простаивающих станков.

### 9. [P2] Неверный индекс слота вызывает исключение на сервере

Место: `Content.Server/_Eclipse/Industrial/IndustrialProcessorSystem.cs:81–85`.

SlotIndex приходит из сетевого сообщения. Проверка index < items.Count пропускает
отрицательные значения, после чего items[index] выбрасывает исключение. Это достижимо
при некорректном сообщении клиента с открытым интерфейсом. Штатный интерфейс отправляет
нормальные индексы, но сервер обязан проверять границы самостоятельно.

Исправление: сначала проверить 0 <= index < число доступных слотов; затем отдельно
обработать занятый и пустой слот. Для ручного извлечения также стоит согласовать
использование checkActionBlocker:false с правилами взаимодействия станции.

### 10. [P2] Планировщик не достигает заявленной пропускной способности

Место: `Content.Shared/_Eclipse/Industrial/PipeTierHelper.cs:14–15`;
`Content.Server/_Eclipse/Industrial/ItemPipeNetworkSystem.cs:242–247`.

Industrial задаёт 3 единицы/с и задержку 0,5 с, Perfect — 6 единиц/с и 0,25 с.
Update делает максимум один перенос после задержки и обнуляет таймер. Даже при
постоянной подаче нескольких источников и свободных получателях верхние пределы
получаются 2 и 4 переноса/с соответственно. Остаток времени кадра также теряется.

Исправление: выбрать одну модель: интервал 1/throughput либо бюджет объёма за время.
Если задержка означает время движения по трубе, моделировать её отдельно от
пропускной способности. Не оставлять два противоречащих друг другу ограничения.

### 11. [P2] Первый непередаваемый продукт блокирует остальные продукты источника

Место: `Content.Server/_Eclipse/Industrial/ItemPipeNetworkSystem.cs:266–285`;
`Content.Server/_Eclipse/Industrial/IndustrialProcessorSystem.cs:375–390`.

Для источника выбирается только первый тип из выходного контейнера. Если для него
нет подходящего свободного получателя, последующие типы продукции этого же станка
не рассматриваются, даже когда для них есть готовый маршрут. Это проявляется у
дробилки со смесью операций: первый выход может ждать заполненную плавильню,
а следующий дроблёный материал мог бы уйти в свободную центрифугу.

Дополнительно сортировка устройств по UID и возврат после первого успеха дают
постоянный приоритет одному источнику. При насыщении пропускной способности он
может не оставлять доли другим.

Исправление: перебирать доступные типы выхода и хранить курсор очередного источника/
получателя, чтобы распределение не зависело постоянно от порядка создания сущностей.

### 12. [P2] Показанные игроку настройки не управляют производством

Место: `Content.Server/_Eclipse/Industrial/IndustrialWorkbenchSystem.cs:56–58`;
`Content.Shared/_Eclipse/Industrial/SharedItemPipeSystem.cs:256–267`;
`Content.Server/_Eclipse/Industrial/ItemPipeNetworkSystem.cs:251–335`.

Клиент отправляет Amount выбранной партии, но сервер использует только RecipeId:
при выборе нескольких изделий запускается изготовление одного. TransferMode трубы
можно менять и видеть при осмотре, но маршрутизация не читает это поле — режимы
Transit/Extract/Insert не меняют фактическую передачу.

Исправление: реализовать выбранное поведение с серверной проверкой количества либо
убрать недействующие элементы управления до появления соответствующей механики.

## Что сохранить

- Прототипы рецептов и компонентов как основную форму описания контента.
- Разделение серверного исполнения и клиентского отображения.
- Подборки и HashSet при построении связности: это обычные структуры графа,
  само их наличие не является переусложнением.
- Последние исправления удаления старых сетей и пропуска неподходящих источников:
  они уже есть в рабочей копии и покрыты имеющимися тестами.
- Небольшие файлы enum и компонентов: для ECS это нормальная организация.

## Порядок исправлений

1. Общие правила идентификации ресурсов, подсчёта и расходования; исправить сырую
   руду, продукцию плавильни, неполные стеки и превышение числа слотов.
2. Согласовать состояния станка: ожидание сырья/питания/тепла/выхода, работа,
   завершение; обеспечить повторный запуск при изменении каждого условия.
3. Ограничить попытки передачи и перестать пересчитывать неизменную топологию.
4. Убрать повторные пересборки, согласовать пропускную способность и очередность.
5. Исправить теплообмен и обновления UI; завершить или убрать неработающие настройки.
6. После этого расширять цепочки и связывать их с научным отделом.

Усложнение пока не требует универсального движка производственных процессов.
Достаточно общих правил ресурсов, явных переходов состояния и отдельного расписания
передач. Физическое перемещение штучных предметов стоит сохранить: текущий путь
удаляет предмет и создаёт новый по прототипу, что при расширении на устройства
с зарядом, повреждениями и содержимым будет сбрасывать их состояние.

## Выполненная проверка

Команда:

```powershell
dotnet test Content.IntegrationTests/Content.IntegrationTests.csproj --no-restore --filter 'FullyQualifiedName~Content.IntegrationTests.Tests.Industrial' --logger 'console;verbosity=minimal'
```

Результат: сборка завершена, 3 тестовых случая прошли, 0 ошибок тестов. Во время
сборки были предупреждения зависимостей и SourceLink; они не помешали запуску.
Тесты проверяют замену/разделение предметных и жидкостных сетей и одну передачу
с пропуском неподходящего источника/заполненного получателя. Они не проверяют
совместимость добытой руды, полный цикл рецептов, прогрев или интерфейс верстака.

Для проверки производительности нужен отдельный сценарий с десятками/сотнями станков:
свободная линия, пустая сеть, забитый выход, массовая установка/удаление труб.
Измерять время систем, аллокации и сетевые обновления. Утверждений о конкретном
проценте ускорения этот аудит не делает.
